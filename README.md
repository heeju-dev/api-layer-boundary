# API Layer Boundary

"팀 컨벤션을 따르는 게 항상 정답인가"를 코드 변경의 파급 범위와 함께 저울질해서, 일부만 적용하기로 판단한 사례를 재구성한 기록입니다.

## 배경 — 팀 컨벤션

이 팀은 "API 함수는 요청만 하고, 응답 가공(본문 추출)·검증은 훅에서 담당한다"는 컨벤션을 갖고 있었습니다.

```ts
// 컨벤션이 기대하는 형태
// api.ts — 요청만
const getGroupList = () => axios.get("/api/groups");

// useGroupList.ts — 가공은 여기서
const useGroupList = () => {
  return useQuery({
    queryKey: ["groupList"],
    queryFn: async () => {
      const res = await getGroupList();
      return res.data.data; // 본문 추출은 훅의 책임
    },
  });
};
```

## 문제

기존 코드 중 일부 API 함수는 이 컨벤션과 다르게, **API 함수 내부에서 이미 응답 본문을 꺼내는 가공**을 하고 있었습니다.

```ts
// 컨벤션과 어긋난 기존 코드
const getGroupList = async () => {
  const res = await axios.get("/api/groups");
  return res.data.data; // 가공이 API 함수 안에 있음
};
```

`async/await`를 걷어내고 컨벤션에 맞추려고 시도하던 중, **본문 추출이 있는 함수에서 `await`를 단순히 제거하면 `Promise`를 그대로 반환하게 되어, 호출부가 값 대신 `Promise` 객체를 받아 `undefined`처럼 동작하는 문제**를 발견했습니다.

## 검토

| 케이스 | 판단 |
|---|---|
| 본문 추출 없이 요청만 하는 함수 | `async/await` 제거 가능 (반환 형태가 안 바뀜) |
| **본문 추출이 있는 함수** | `await`가 필수라 단순 제거 불가. 컨벤션대로 맞추려면 가공 로직을 훅으로 옮겨야 함 |

가공 로직을 훅으로 옮기려면, 그 API 함수를 사용하는 **모든 호출부(다른 훅, 다른 화면)의 접근 경로가 한 단계씩 밀려야** 합니다. 예를 들어 `list.name`으로 접근하던 곳을 전부 `list.data.name`으로 바꿔야 하는 식으로, 변경 범위가 API 함수 하나가 아니라 그걸 쓰는 모든 곳으로 퍼집니다.

## 최종 판단

파급 범위를 확인한 뒤, **안정적으로 잘 돌고 있는 조회 함수는 그대로 두고, 위험이 낮은(호출부가 적거나 영향이 명확한) 함수만** 컨벤션에 맞게 조정하는 선에서 마무리했습니다.

## 왜 이 방식을 선택했는가

컨벤션을 지키는 것 자체는 맞는 방향이지만, "지금 당장 전부 통일해야 하는가"는 별개의 질문이라고 판단했습니다.

- 반환 형태가 바뀌는 변경은 그 함수를 쓰는 모든 소비처를 **동시에** 고쳐야 안전합니다. 한 곳이라도 놓치면 런타임에만 드러나는 버그가 생깁니다.
- 이미 안정적으로 동작 중인 코드를, 컨벤션 통일이라는 목적만으로 넓은 범위까지 건드리는 건 **이득 대비 리스크가 큰 변경**이라고 봤습니다.
- 대신 새로 작성하거나 어차피 손대야 하는 코드는 처음부터 컨벤션에 맞게 작성해서, 무리한 일괄 변경 없이도 점진적으로 통일되도록 했습니다.

## 배운 점

팀 컨벤션은 지켜야 하는 규칙이지만, "지금 이 변경이 그 규칙을 지키기 위해 감수해야 할 위험보다 가치가 큰가"는 매번 따로 판단해야 한다는 걸 확인했습니다. `async` 필요 여부가 "누가 호출하는가"가 아니라 "함수 몸통 안에서 `await`를 쓰는가"로 결정된다는 것도, 리팩토링 범위를 판단하는 데 중요한 기준이었습니다.
